# RAG Hybrid 检索案例研究：RRF 失败分析与"骨架+补位"修正

> 面试分享用案例文档。项目：电商客服 Agent（LangGraph + RAG + 评测闭环）。
> 数据均可复现：`app/agent/rag/eval/` 下 run_eval 脚本，32 条评测集，41 chunks 知识库，本地 bge 推理，零 API 成本。

## 1. 背景与基线

**检索链路（改造前）**：用户问题 → bge-small-zh-v1.5 本地向量编码 → 余弦相似度 → Top-5 chunk 交给 LLM 生成回答。这是标准的 dense（稠密向量）检索。

**基线成绩**（32 条评测集，检索层指标，无 LLM judge）：

| 指标 | 数值 | 含义 |
|---|---|---|
| hit@5 | 1.000 | 每条问题至少命中 1 个正确 chunk |
| MRR@5 | 0.887 | 首个正确 chunk 的平均排名（越接近 1 越靠前） |
| recall@1 | 0.774 | 77.4% 的问题第 1 名就是正确 chunk |
| recall@5 | 0.946 | 正确 chunk 的整体覆盖率 |

**问题**：recall@5 没到 1.0，逐 case 错误分析发现缺失 gold 的失败模式是——**正确答案在语义上与相邻章节过于接近，被兄弟章节挤出 top-5**。例如问"会员升级需要多少成长值"，gold 有两个 chunk：「等级体系」章节（含"成长值达到5000"）和「常见问题」章节。常见问题稳在第 1，而等级体系被兄弟章节挤到第 6 名——缺失的正是它。

## 2. 尝试的方案：BM25 + RRF 标准融合

**动机**：向量检索擅长同义改写（"邮费"≈"运费"），但对专有名词、数字门槛等**词汇信号**不敏感。BM25（关键词精确匹配打分，jieba 分词）恰好互补。

**实现**：
- dense 路向量检索 + sparse 路 BM25 各取 top-10 候选
- 用业界标准 RRF（Reciprocal Rank Fusion）融合：`score(chunk) = Σ 1/(60 + rank)`，两路名次相加，取 top-5
- 知识库 41 chunks，两路索引 chunk_id 完全对齐（同一批切分产物），保证融合时能识别"同一条知识"

**实测结果 vs 基线**：

| 指标 | 基线（纯 dense） | RRF 融合 | 变化 |
|---|---|---|---|
| hit@5 | 1.000 | **0.968** | ↓ 1 条问题所有 gold 跌出 top-5 |
| MRR@5 | 0.887 | **0.847** | ↓ |
| recall@5 | 0.946 | **0.919** | ↓ |
| 延迟 | 14ms/条 | 15ms/条 | 持平 |

**结论：全面回退，方案否决。**

## 3. 回退的根因分析

### 3.1 机制：加性融合的结构性缺陷

逐 case 对比两路排名后发现，3 条 case 回归、全部是同一个病根：

1. **k=60 把 dense 自己的名次差距抹平了**——RRF 里第 1 名得 1/61，第 6 名得 1/66，只差 5%。dense 排名的"确定性"在融合分数里几乎消失。
2. **BM25 在 41 chunks 小库上噪声很大**——FAQ 类 chunk 靠"怎么""快递"这类通用词就能排进 BM25 前几名。
3. 两者叠加：一个 dense 排 6-10 名的垃圾 chunk，只要 BM25 强命中，融合分接近翻倍（≈1/66+1/61≈0.031），**反超 dense 第 1 名但 BM25 搜不到的正确答案**（只有 1/61≈0.016）。

关键在于：**正确答案经常恰好是 BM25 搜不到的**——因为它的问题是语义型的（"丰巢忘取件"），字面上与正确 chunk 无词汇重叠。这正是当初要用向量检索的原因，而 RRF 融合又把劣势放大了回去。

### 3.2 典型例子（q_033）

查询："快递放丰巢了，我忙忘了，多久不取会有问题？"（gold：配送说明#05-01，讲超时未取件的处理）

| chunk | dense 排名 | BM25 排名 | 融合结果 |
|---|---|---|---|
| **配送说明#05-01（gold）** | **1** | **前 10 都没有** | 被挤出 top-5 ✗ |
| 常见问题FAQ#03-02（垃圾） | 6-10 | **1** | 冲到第 2 |
| 常见问题FAQ#03-00（垃圾） | 6-10 | **2** | 冲到第 1 |

垃圾 chunk 凭"dense 尾部 + BM25 头部"双份加分，把 dense 冠军挤下了台。

### 3.3 数学上加权 RRF 也救不了

尝试给 dense 加权（w_dense=0.7 甚至 0.9）：垃圾 chunk = w_d/66 + w_s/61，正确答案 = w_d/61。只要 w_s > 0，dense 第 6 名 + BM25 第 1 名的组合依然能翻越 dense 第 1 名——**因为 dense 1~10 名之间的 RRF 分差本身只有 10%，任何 sparse 加分都能翻转它**。这是加性排名融合的结构性问题，不是参数调优问题。

## 4. 修正方案：dense 保底 + sparse 补位

放弃"平等融合"，改为**主从结构**：

```
1. dense top-5 为骨架，顺序不动（头部绝不被 sparse 洗掉）
2. sparse 只做一件事：补位
   候选须同时满足两个独立信号：
   a) BM25 top-2 强命中（词汇证据）
   b) dense 排 6-10 名（语义证据：相关但差一名）
   → 替换 dense 第 5 名，至多补一个
3. BM25 top-10 之外 / dense top-10 之外的 chunk 不参与（垃圾防火墙）
```

**为什么这样能识别"被挤掉的答案"**：检索时并不知道正确答案是什么，但"语义上相关（dense 6-10）+ 关键词精确命中（BM25 top-2）"两个来自互不相干信息源的信号同时出现，是"差一名被挤掉"的强特征。实例：q_011 问"成长值5000"，正确 chunk dense 第 6（被兄弟章节挤）+ BM25 第 2（"成长值""5000"字面命中）→ 双信号命中 → 捞回。

**风险封顶**：dense top-4 永不动（头部零风险）；至多补 1 个、只动末位（最坏 recall 损失 1/5）；双重过滤垃圾。

**全量 32 条实测验证**（本地 bge 推理，`--no-judge`，结果目录 `app/agent/rag/eval/results/hybrid-v2-top5`）：

| 方案 | hit@5 | MRR@5 | recall@1 | recall@5 |
|---|---|---|---|---|
| 基线（纯 dense） | 1.0000 | 0.8870 | 0.7740 | 0.9460 |
| RRF（实测，否决） | 0.9677 | 0.8468 | — | 0.9194 |
| **保底+补位（实测）** | **1.0000** | **0.8871** | **0.7742** | **0.9624** |

实测精确复现离线模拟的结论：四项底线全部保持，recall@5 净增 1.6pt。

补位生效的直接证据（q_011）：基线 top-5 第 5 名是非 gold 的「积分体系」章节，实测被替换为 gold「等级体系」章节（dense 第 6 + BM25 第 2，双信号命中），缺失 gold 回收。

延迟：稳态约 17ms/条（基线约 14ms，BM25 分词开销约 +3ms；summary 均值被首条本地模型加载 ~19s 摊高，对比以稳态为准）。

## 5. Rerank 精排：从探针到生产接入

补位只解决「gold 被挤出 top-5」（recall@5），管不了「gold 已在 top-5 但排名不优」（recall@1）——q_020/q_034 的 gold 都卡在第 2。CrossEncoder（bge-reranker-base）对 (query, chunk) 做逐 token 交叉注意力，能区分「主题相同」与「答案所在」。

**探针实验**（`tests/test_reranker.py`，不动生产代码）：候选池=生产 chroma dense top-5，正文全文参与打分，逐 case 记录 chunk_id/dense 原排名/rerank 分数/新排名。结果：recall@1 0.7204→**0.8387**（+11.8pt）、MRR@5 0.8871→**0.9677**；q_020/q_034 的 gold 均由第 2 →第 1；recall@5 纹丝不动（rerank 不改候选集）。

**生产接入**（方案 A：补位 → 精排）：dense top-10 → BM25 补位 → CrossEncoder 对最终 top-5 精排。`Reranker` 随 `_get_retriever` 单例缓存；`retrieval_mode=hybrid_rerank` 一行开关；精排只调顺序不改候选集，同分按 chunk_id 保确定性，`score` 字段保留 dense 分。

**全链路三模式对比（32 条全量实测）**：

| 指标 | dense 基线 | hybrid 补位 | hybrid_rerank |
|---|---|---|---|
| recall@1 | 0.7742 | 0.7742 | **0.8387**（+6.5pt） |
| MRR@5 | 0.8870 | 0.8871 | **0.9677**（+8.1pt） |
| recall@5 | 0.9462 | 0.9624 | **0.9624**（补位收益无损保留） |
| hit@5 | 1.0 | 1.0 | 1.0 |

- **探针→生产无损**：全链路 recall@1 与探针完全一致——补位捞回的候选没有抢夺其他 case 的首位，精排增益完整落地
- 重点 case：q_020（02-01 → 第 1）、q_034（05-02 → 第 1）、q_011 双 gold 全进 top-3（补位捞回的 01-00 精排后站到第 3）
- 延迟：稳态 ~700ms/条（CPU 5 对 CrossEncoder 前向；首条 ~30s 含模型加载）——本地 CPU 真实成本，生产可换 GPU 或 API 化
- **取舍记录**：方案 B（rerank 对 top-10 全重排取 top-5，可能省掉补位规则）未验证即跳过，选择「两半各自已验证」的保守组合；B 的价值留作后续实验

### 5.1 端到端 A/B 对照（2026-10-28）

检索层指标提升是否传导到回答质量？A/B 对照：A 组=`dense`，B 组=`hybrid_rerank`，同 32 条、同生成模型（deepseek-v4-flash）、同 prompt、top-k=3，唯一变量是检索模式。生成层评分用**自写 LLM judge**（ragas 依赖链与本地 bge 栈冲突被移除）：faithfulness（断言被 context 支持占比）+ answer_correctness（reference 事实点覆盖占比），每题各 1 次调用。

| 层 | 指标 | A: dense | B: hybrid_rerank | 变化 |
|---|---|---|---|---|
| 检索 | MRR@3 | 0.8871 | **0.9839** | +9.7pt |
| 检索 | recall@3 | 0.9140 | 0.9301 | +1.6pt |
| judge | answer_correctness | 0.8339 | **0.8634** | **+3.0pt** |
| judge | faithfulness | 0.9280 | 0.9126 | -1.5pt |
| 成本 | 检索稳态延迟 | ~26ms | ~700ms | +rerank CPU 推理 |

**传导证据链**（per-case）：
- **q_011（组合收益兑现）**：补位把 gold 01-00 捞进 top-5（第 5 位），rerank 再把它顶到 **top-3 第 2**——原以为 top-3 口径下补位收益会丢，实际「补位→精排」的组合让 gold 双双在场，correctness 0.4→0.8。A 方案的价值在此案例闭环
- q_018：gold 01-01 从第 2 →第 1，correctness 0.5→1.0
- 6/32 条 top1 发生变化，涨跌相抵后净改善

**噪声管理教训**：
- LLM judge 单条波动巨大：q_037 两组 top3 完全相同、correctness 均 1.0，faithfulness 却 1.0→0.4（同输入不同判定）——单条 judge 读数不可信，**组均值（31 条）才是可靠口径**，faithfulness -1.5pt 大概率是噪声而非退化
- temperature=0 不等于确定性：q_029 两组 top1 相同（gold 已在第 1）correctness 仍 0.6→1.0，生成模型输出本身有随机性
- 结论：A/B 差异要看方向（correctness +3.0pt）+ 传导路径（q_011/q_018 可解释）+ 噪声上界（judge 单条 ±0.6）三重验证，不能只看均值数字

## 7. 面试讲点提炼

1. **先评测后优化**：没有 32 条评测集和基线数字，就发现不了"标准方案反而变差"这类反直觉结论。
2. **反直觉结论 + 根因到数学层面**：RRF 是教科书方案，但 k=60 的平滑性 + 小库 BM25 高噪声，使加性融合结构性失效；能推出"w_s>0 必然翻转 dense 头部"这个数学论证。
3. **从错误分析到设计**：不是调参救 RRF，而是根据失败模式（垃圾靠双路加分翻倍）反向设计"主从结构 + 双独立信号 + 结构封顶"。
4. **承认方案的局限**：补位策略修不了跨文档干扰，明确给出下一阶段 rerank 的分工与理由（后经探针实验验证：recall@1 +11.8pt）。
5. **工程闭环**：索引 chunk_id 对齐、稳态延迟 ~17ms、双后端可切换、全部离线可复现；离线模拟的结论被全量实测逐位复现（模拟 → 实测两级验证）。
6. **指标口径决定结论**：hit@k 对多 gold 过于宽松，before 侧已打满分、rerank"看起来无效"；换成位置敏感指标（recall@1/MRR）立刻看出 +11.8pt——评估指标选错，有效优化会被误判为无效。
7. **方案互补性用数据证明**：rerank 后 recall@5 纹丝不动，直接证明 rerank 与补位的分工边界（一个管排序质量、一个管候选覆盖），而不是拍脑袋说"都上"。
8. **探针→生产无损迁移**：先独立探针验证组件价值，再以可选注入接入生产链路，全链路 recall@1 与探针完全一致——组件级验证与系统集成解耦，收益不因组合而损耗；同时诚实记录延迟成本（CPU 稳态 ~700ms/条）与未走的路线（方案 B）。
