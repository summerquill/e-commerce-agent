# 上下文压缩案例研究：先建度量，再用 pinned facts 补"摘要丢事实"

> 面试分享用案例文档。项目：电商客服 Agent（多轮对话记忆线）。
> 数据均可复现：`app/agent/memory/eval/` 下离线 harness（零 API），LLM 对照每组 12 次调用，结果 JSON 全落盘。

## 1. 30 秒电梯稿（面试口语版）

"我的客服 Agent 是多轮对话，上下文会一直涨，所以做了滚动摘要压缩：消息超过 10 条就把老消息压成一段摘要，只保留最近 3 条原文。但摘要是有损的——**我想知道它到底丢了什么、丢了多少，而不是假装它没问题**。所以我先搭了一个压缩评测 harness 再谈优化。

harness 的核心是『评测的就是生产代码』：压缩触发、切分逻辑直接复用生产函数，外加等价性单测保证两条路径一致；在对话脚本里埋点 25 条 gold 事实做确定性断言。跑真实 LLM 基线时拿到两个硬证据：**一是递归压缩有真实漂移**——企业采购脚本第 4 轮重写摘要时把整条售后承诺线丢了；**二是 prompt 里写『不超过 300 字』根本管不住模型**，12 轮里 4 轮超限。还有个坑：temperature 0.3 下同一脚本跑两次，一次丢 1 条事实、一次丢 3 条——单跑读数不可信。

针对证据我做了一个针对性升级：**pinned facts**。订单号、税号这类实体用正则从对话里抽出来，原文钉进一个独立 system 段，摘要随便压，实体永远在；摘要再加 400 字代码级硬截断兜底。改完对照：实体类事实从『看模型这次心情』变成 8/8 结构性保证全保，语义承诺类保留率 62.5% → 87.5%，代价是压缩比 2.98x → 2.36x——锚点段是占上下文的，这个成本我不藏，直接算进压缩比分母。"

## 2. 背景与问题

**压缩链路（优化前）**：每轮对话结束检查 `len(messages) > threshold(10)` → `split_history` 切分（切分点回退跳过 tool 消息，防止工具结果和它的调用参数被拆到两侧）→ 老消息交 LLM 重写为摘要（递归：携带上一版摘要）→ 保留最近 k=3 条原文。下轮请求时消息列表 = system + 记忆区 + **摘要** + 原始窗口。

**风险**：摘要是 LLM 有损重写，且是**摘要的摘要**——每轮压缩都在上一版摘要基础上重写，任何一轮丢掉的信息后面再也回不来。

## 3. 评测设计先行（为什么 harness 比优化先做）

没有度量就无法证明优化有效，也无法定位"该优化什么"。harness 三个设计决策，每个都是面试讲点：

### 3.1 指标定义与"为什么需要它"

| 指标 | 定义 | 为什么必要 |
|---|---|---|
| **summary_reliant_retention** | 已被压出窗口、只能靠摘要挽回的事实保留率 | **核心指标**。还留在窗口里的事实不考验摘要能力，只有它衡量"摘要本身的质量"，有区分度 |
| final retention | 摘要 ∪ 窗口的事实保留率 | 总量兜底指标，防止窗口掩盖摘要问题 |
| compression_ratio | 原始字符数 /（摘要 + 锚点段 + 窗口字符数） | 收益端。**分母必须包含锚点段**——优化不能只报收益不报成本 |
| decay_curve | 按压缩轮次对齐的保留率 | 定位漂移发生在第几轮 → 证明病灶是"递归重写"而非单次摘要 |
| retention_by_category | 实体 / 承诺 / 身份 等分类保留率（跨脚本 pooling） | **决定优化方向**：实体类丢 → 正则锚定可解；语义承诺类丢 → 只能靠结构化摘要。分类数据直接催生了 pinned facts 方案 |

### 3.2 『评测的就是生产代码』

- `split_history` / `build_transcript` 抽为公共函数，生产 `_compress_history` 与评测 runner 共用；
- `EcomAgent` 等价性单测：同一输入下生产压缩路径与 runner 行为逐位一致；
- 这保证 harness 测出来的数字就是线上行为，不存在"评测版比生产版干净"的偏差。

### 3.3 确定性 factcheck + 全落盘 trace

- gold 匹配是空白归一化子串匹配，**不调 LLM 判定**——订单号这类实体的"是否还在"不需要语义判断，确定性断言让 26 个离线单测秒级可跑；
- 中间踩过一个真 bug：LLM 重写摘要时把「100 元无门槛」写成「100元无门槛」，逐字面匹配漏报已保留事实（假阴性）。回查落盘的 trace 定位根因，修复为空白归一化 + 回归用例。**没有全量 trace 落盘这个 bug 根本查不了**；
- 每轮压缩的 `input_messages` + summary 全文 + 当时锚点列表全部落 JSON，事后任何读数都能回溯到原始输入。

## 4. 基线数据与两大发现

LLM 基线（deepseek-v4-flash，t=10/k=3，3 个长脚本 38~42 条消息 × 4 轮 = 12 次摘要调用）：

| 指标 | A1（基线首跑） |
|---|---|
| final retention | 96.3% |
| summary_reliant | 95.83% |
| 压缩比 | 2.64x |
| 衰减曲线 | 0.60 → 0.68 → 0.72 → 0.80 |

数字看着不错，但逐脚本拆开拿到两个改变方案的发现：

**发现①：递归压缩真实漂移**。企业采购脚本 b2b 第 4 轮重写摘要时整条丢弃售后承诺线（`promise_install` 丢失）。衰减曲线显示保留率逐轮下降，说明损伤随重写累积。

**发现②：prompt 级长度约束不可靠**。SUMMARY_PROMPT 明确要求 ≤300 字，12 轮里 4 轮超限（max 367 字）。指令约束没有强制力，长度控制必须代码级兜底。

**附加发现：单跑方差大**。为对照实验复测的第二组（A2，配置与 A1 完全相同）只有 87.5%——同一模型同一脚本，一次丢 1 条、一次丢 3 条。结论：**temperature>0 的摘要器，结论必须看多跑分组，不能引用单跑读数**。

## 5. 优化：pinned facts 实体锚定 + 硬截断

机制（`app/agent/pinned.py`）：

1. **抽取**：确定性正则，不调 LLM——锚点机制自身必须可靠且可复现。订单号/运单号/机型序列号/税号（字母数字双含、去连字符 ≥8 位）、纯数字 ≥6 位（手机号/纯数字单号）、邮箱；日期（2025-11-03）、时间区间（14:00-18:00）、金额天然不命中；
2. **合并**：跨压缩轮次去重，FIFO 上限 30 条（防 system 段膨胀，近期单号更常被追问）；
3. **注入**：独立 system 段「关键信息锚点」置于摘要之后，与摘要构成**「有损摘要 + 无损锚点」双通道**；
4. **兜底**：`summarize()` 加 `hard_cap=400` 代码级截断，不再依赖 prompt 自觉。

**设计取舍（追问高发区）**：为什么不用 LLM 抽实体？——抽取结果会进锚点段成为"事实源"，若抽取本身是 LLM 的，锚点的可靠性就退化为另一个概率问题；正则对结构化标识符是精确解。语义承诺（"15 天无理由"）表述多样、正则覆盖不了，**诚实地留给摘要通道，由分类别指标暴露它的保留率**。

## 6. A/B 对照结果与 metric 变化

三组同配置（t=10/k=3，各 12 次调用）：A1 首跑、A2 复测（估方差）、B 组（pin + hard_cap）：

| 指标 | A1 基线 | A2 复测 | B（pin+cap） | 变化解读 |
|---|---|---|---|---|
| final retention | 96.3% | 88.89% | 96.3% | B 与 A1 持平，但含金量不同（见下） |
| summary_reliant | 95.83% | 87.5% | 95.83% | 对 A2 提升 8.3pt |
| **promise 类（8 条）** | 87.5%（丢1） | **62.5%（丢3）** | **87.5%（丢1）** | 语义承诺仍靠摘要，但 B 稳定在 A1 水平 |
| **非 promise 17 条** | 100% | 100% | 100% | 全程无丢失，其中实体类由**代码保证** |
| 锚点覆盖 | — | — | 8/8 实体入锚 | 订单号/序列号/税号全部命中 |
| 压缩比 | 2.64x | 2.98x | 2.36x | 锚点段成本 ~0.3~0.6x，明算账 |
| 摘要超 300 字轮数 | 4/12（max 367） | 3/12（max 358） | 0/12（max 347） | 400 硬顶留余量，未触发截断 |

**怎么读这张表（关键叙事）**：

1. **A1 vs A2 是方差组**：配置相同读数差 7.5pt，证明单跑不可信——这也是为什么对照实验跑了三组而不是两组；
2. **B 的 95.83% 和 A1 的 95.83% 不是一回事**：A1 是"这次运气好没丢"，B 的实体保留是**结构性保证**（哪怕摘要丢了也能从锚点找回）——同样的数字，可靠性语义完全不同，这是面试时最值得讲的一点；
3. **A2 暴露了最坏情况**：b2b 脚本一轮丢 3 条承诺，而 B 组在同样方差环境下 promise 类稳定在 7/8，仅剩 `invoice_type`（增值税专票）这种纯语义承诺偶发丢失；
4. **压缩比代价透明**：2.98x → 2.36x，锚点段每脚本约 150 字符。收益（实体 0 风险 + 方差下限抬高）对客服场景（订单号是最高频追问）完全值得。

## 7. 诚实的 trade-off 与遗留

- **语义承诺类仍会丢**：`invoice_type` 这类无结构化特征的承诺不可正则锚定，目前靠摘要通道 + 分类指标暴露。下一步候选是**结构化摘要**（摘要输出字段化模板：订单/承诺/偏好分栏），让承诺也有槽位兜底；
- **硬截断本轮未实际触发**（max 347 < 400），它是保险而非收益来源——但发现①②说明没有它就是在裸奔；
- **实体误报可接受**：弱 token（如 wifi6password，仅 1 个数字）通过"字母数字各 ≥2"规则排除；紧凑日期会被钉住，属无害误报；
- **评测本身的天花板**：gold 是最小关键字符串匹配，"语义等价改写"（换个说法但意思对）会漏报为丢失——这是确定性断言换 LLM judge 的主动取舍：可复现、零成本、秒级，且对"实体是否原文在场"这个核心问题足够。

## 8. 面试追问 Q&A 备忘

- **为什么压缩触发用消息条数不用 token？** 教学项目用条数近似阈值，token 计数是 obvious 升级项（tiktoken 一行），机制设计与触发条件解耦，不影响 harness 复用；
- **为什么保留窗口 k=3 而不是动态？** k 是 harness 的实验变量（CLI 可调），固定值保证 A/B 可比；
- **pinned 淘汰策略？** FIFO 上限 30：防膨胀优先，客服场景近期订单更常被追问，淘汰最旧符合业务直觉；
- **和 LangGraph checkpointer 的关系？** 正交：checkpointer 管跨进程状态恢复，压缩管单会话内上下文预算；
- **这个 harness 还能评什么？** 任何 `(old_messages, prev_summary) -> str` 的摘要器都能插进来对比（离线 truncate/extractive 基线已内置），后续 plan_execute 路径的 step_results 紧缩也计划复用同一套方法。
