# 上下文压缩案例研究：先建度量，再用 pinned facts 补"摘要丢事实"

> 面试分享用案例文档。项目：电商客服 Agent（多轮对话记忆线）。
> 数据均可复现：`app/agent/memory/eval/` 下离线 harness（零 API），LLM 对照每组 12 次调用，结果 JSON 全落盘。

## 1. 30 秒电梯稿（面试口语版）

"我的客服 Agent 是多轮对话，上下文会一直涨，所以做了滚动摘要压缩：消息超过 10 条就把老消息压成一段摘要，只保留最近 3 条原文。但摘要是有损的——**我想知道它到底丢了什么、丢了多少，而不是假装它没问题**。所以我先搭了一个压缩评测 harness 再谈优化。

harness 的关键是控制评测偏差：我把最容易测偏的核心压缩逻辑（历史切分、transcript 构造）抽成了生产与评测共用的函数，再用等价性单测验证两条路径在这些关键环节行为一致（注意不是整个系统所有行为一致——事实检查、指标聚合是评测自有逻辑）；然后在对话脚本里埋点 25 条 gold 事实做确定性断言。跑真实 LLM 基线时拿到两个硬证据：**一是递归压缩有真实漂移**——事实级轨迹显示，企业采购脚本前三轮摘要一直保留的三条承诺，第 4 轮重写后被一次性全部抹掉；**二是 prompt 里写『不超过 300 字』管不住模型**，三组共 36 轮压缩里 11 轮超限。还有个坑：temperature 0.3 下同一脚本跑两次，一次丢 1 条事实、一次丢 3 条——单次运行不足以代表稳定表现，所以我保留了复测组并把所有差值当点估计。

针对证据我做了一个针对性升级：**pinned facts**。订单号、税号这类实体用正则从对话里抽出来，原文钉进一个独立 system 段，与摘要构成双通道；摘要再加 400 字代码级硬截断兜底。机制结果：评测集 8 条目标实体 8/8 入锚，实体是否存活不再完全依赖摘要保留原文。但有两句诚实的话必须说：本轮所有运行的摘要恰好都保住了全部实体，**锚点没有产生可实测的增量挽回，它的价值是独立于摘要的结构保险**；承诺类保留率回到首跑水平是运行间波动，**不能归因于锚点**。代价是压缩比从基线 2.64x 降到 2.36x——锚点段占上下文，成本算进压缩比分母，不藏。"

## 2. 背景与问题

**压缩链路（优化前）**：每轮对话结束检查 `len(messages) > threshold(10)` → `split_history` 切分（切分点回退跳过 tool 消息，防止工具结果和它的调用参数被拆到两侧）→ 老消息交 LLM 重写为摘要（递归：携带上一版摘要）→ 保留最近 k=3 条原文。下轮请求时消息列表 = system + 记忆区 + **摘要** + 原始窗口。

**风险**：摘要是 LLM 有损重写，且是**摘要的摘要**——每轮压缩都在上一版摘要基础上重写，任何一轮丢掉的信息后面再也回不来。

## 3. 评测设计先行（为什么 harness 比优化先做）

没有度量就无法证明优化有效，也无法定位"该优化什么"。harness 三个设计决策，每个都是面试讲点：

### 3.1 指标定义与口径（先说清楚怎么算，再说为什么看）

**口径约定**（面试官最容易抓的地方，先钉死）：

- 事实保留的判定单位是**条**：某条 gold 事实若出现在「摘要文本 ∪ 最终窗口消息」中（空白归一化后的子串匹配）记为 retained；
- **per-script 口径**：分母 = 该脚本的 gold 事实总数（三个脚本分别为 8 / 8 / 9 条）；
- **aggregate 默认 macro 平均**：3 个脚本的 per-script 值等权平均。选 macro 是为了脚本等权—— pooled 会按事实数加权（9 条的 b2b 权重最大），单脚本失守被放大；同时每个 pooled 数字都给出对照，两个口径结论一致；
- 25 条事实的总量很小，**这是样本量约束，所有结论的置信度受此限制**（详见 §6.2 结论边界）。

| 指标 | 精确定义与计算 | 为什么看它 |
|---|---|---|
| **final retention** | per-script = retained / 该脚本事实总数；aggregate = 3 脚本 macro 平均。A1 = (8/8 + 8/8 + 8/9)/3 = **96.3%**；pooled 对照 = 24/25 = **96.0%** | 总量兜底指标：不管信息是从哪条通道找回的，先看最终还剩多少 |
| **summary_reliant_retention** | 分母 = **不在最终窗口内**的事实（per-script 分母 4 / 5 / 8，合计 17 条）。**分母归属只看窗口消息、与摘要保留与否无关**（`in_window` 由窗口文本独立判定），无选择偏差。分子口径必须区分两个通道：A1/A2 度量的是**纯摘要**找回；B 组代码实现把锚点段与摘要合并检查，准确名称是 **context_recoverability**（从摘要或锚点找回）。两组数字本实验恰好相同（B 组纯摘要重算 = 混合口径，见 §6 解读②），但语义不能混用 | **核心指标**。还在窗口里的事实靠原文存活，不考验摘要能力；只有被压出窗口的事实才度量持久上下文的质量。**注意分母只有 17 条：1 条事实的进出 = ±5.9pt**，必须配合分类别口径和多次重跑一起读，单跑单值没有意义 |
| **compression_ratio** | 原始全部消息字符数 /（final_summary + 锚点段 + 窗口消息字符数）。**锚点段计入分母** | 收益端指标。优化不能只报收益不报成本——锚点注入是真实占用的上下文 |
| **decay_curve / 事实轨迹** | 按压缩轮次对齐的 macro retention（第 i 轮取各脚本该轮快照均值），以及**单条 gold 在逐轮摘要中的出现轨迹** | 定位单条事实"哪轮还在、哪轮被抹"。**宏观 decay 曲线在本数据集上有伪影**：早期轮次大量事实尚未在对话中发生，读数偏低，曲线呈上升趋势——它不能被解读为"压缩质量逐轮变化"（无论变好或变坏），可靠的是逐条轨迹（如 b2b 三条承诺 round1-3 在、round4 全消，见 §4 发现①） |
| **retention_by_category** | 按 fact.category 分组，**跨脚本合并计数（pooling）**：A1 promise = 7/8 | 决定优化方向：实体类丢 → 正则锚定可解；语义承诺类丢 → 只能靠摘要/结构化摘要。不用 macro：单脚本单类别仅 1~4 条，均值方差爆炸 |

> 为什么 summary_reliant 是核心而 final 不是：final retention 混合了"窗口救命"和"后续通道救命"两种成分，窗口越大它越好看但与压缩质量无关；summary_reliant 剥离了窗口成分，唯一直接度量"被压出窗口的事实能否从持久上下文找回"。pin 模式下它是 context_recoverability（锚点+摘要），与纯摘要质量的区分见 §6。

### 3.2 生产与评测的关系：共享什么、验证什么、各自管什么（验证边界）

不把这套关系说成"整个系统和评测完全一致"——它的准确边界分三层：

**第一层：真正的共享代码（同一份函数，两处 import）**

- `split_history`：切分点计算 + tool 消息回退逻辑——这是最容易产生评测偏差的部分（切分点错一条，事实归属就全错），抽成 `app/agent/summarizer.py` 的公共函数，生产 `_compress_history` 和评测 runner 都调它；
- `build_transcript`：消息列表 → LLM 可读文本的渲染规则（tool_calls 参数保留、tool 结果截断），同样两处共用——渲染不一致会导致"评测喂给摘要器的输入和生产不一样"。

**第二层：等价性单测验证的内容**

`tests/test_compression_eval.py` 的 `TestAgentEquivalence`：给定同一组 6 条消息，断言 (a) 生产路径 `EcomAgent._compress_history()` 的切分结果与直接调用 `split_history` 逐位一致（old/recent 边界与内容）；(b) 压缩后 `agent.summary` 文本与 `agent.raw_messages` 窗口状态符合 runner 的预期行为。**它证明的是"在这两个关键环节上，生产路径与评测路径行为一致"，不证明、也不需要证明 factcheck 和聚合逻辑与生产一致**——那本来就不是生产系统的组成部分。

**第三层：runner 独立控制的评测自有逻辑**

- `summarize_fn` 以函数注入（生产传真实 client，评测可传离线基线或桩）；
- gold 事实检查（factcheck）、指标计算与聚合、trace 落盘——这些是评测的组成部件，不与生产共享，也不应该共享。

一句话版本："**我把容易产生评测偏差的核心压缩逻辑抽成了共享函数，并通过等价性测试验证生产路径与评测路径在这些关键环节的行为一致。**"

### 3.3 确定性 factcheck + 全落盘 trace

- gold 匹配是空白归一化子串匹配，**不调 LLM 判定**——订单号这类实体的"是否还在"不需要语义判断，确定性断言让 26 个离线单测秒级可跑；
- 中间踩过一个真 bug：LLM 重写摘要时把「100 元无门槛」写成「100元无门槛」，逐字面匹配漏报已保留事实（假阴性）。回查落盘的 trace 定位根因，修复为空白归一化 + 回归用例。**没有全量 trace 落盘这个 bug 根本查不了**；
- 每轮压缩的 `input_messages` + summary 全文 + 当时锚点列表全部落 JSON，事后任何读数都能回溯到原始输入。

## 4. 基线数据与两大发现

LLM 基线（deepseek-v4-flash，t=10/k=3，3 个长脚本 38~42 条消息 × 4 轮 = 12 次摘要调用）：

| 指标 | A1（基线首跑） |
|---|---|
| final retention | 96.3%（macro；pooled 24/25 = 96.0%） |
| summary_reliant | 95.83%（macro；pooled 16/17 = 94.1%） |
| 压缩比 | 2.64x |
| 衰减曲线 | 0.60 → 0.68 → 0.72 → 0.80 |

数字看着不错，但逐脚本拆开拿到两个改变方案的发现：

**发现①：递归压缩真实漂移（证据是事实级轨迹，不是宏观曲线）**。对逐轮落盘的摘要做单条 gold 轨迹检查，企业采购脚本（b2b）暴露两种丢法：**A2 组**的三条承诺（送装、远程售后、增值税专票）在 round1~3 的摘要中连续在场，**round4 一次重写后被同时抹掉**——一版摘要就能把此前多轮保留的信息整体抹除；**A1 组**的 `promise_install` 在 round1~2 在场，round3 被重写抹掉且后续未恢复。两者共同指向递归重写的结构性风险。（注：宏观 decay 曲线 0.60→0.68→0.72→0.80 呈上升趋势，那是早期轮次大量事实尚未在对话中发生的评测伪影，不能读作"压缩质量逐轮变化"，可靠证据只有逐条轨迹。）

**发现②：prompt 级长度约束不可靠（三组一致）**。SUMMARY_PROMPT 明确要求 ≤300 字，三组共 36 轮压缩中 11 轮超限（A1 4/12、A2 3/12、B 4/12，max 367 字）。指令约束没有强制力，长度控制必须代码级兜底。

**附加发现：同配置两次运行读数明显不同**。复测组（A2，配置与 A1 完全相同）final retention 88.89% vs 首跑 96.3%——同一模型同一脚本，一次丢 1 条事实、一次丢 3 条。处理方式：**在当前配置下，单次运行不足以代表稳定表现**，因此对照实验保留复测组，所有组间差值视为点估计而非稳定性能承诺。

## 5. 优化：pinned facts 实体锚定 + 硬截断

机制（`app/agent/pinned.py`）：

1. **抽取**：确定性正则，不调 LLM——锚点机制自身必须可靠且可复现。订单号/运单号/机型序列号/税号（字母数字双含、去连字符 ≥8 位）、纯数字 ≥6 位（手机号/纯数字单号）、邮箱；日期（2025-11-03）、时间区间（14:00-18:00）、金额天然不命中；
2. **合并**：跨压缩轮次去重，FIFO 上限 30 条（防 system 段膨胀，近期单号更常被追问）；
3. **注入**：独立 system 段「关键信息锚点」置于摘要之后，与摘要构成**「有损摘要 + 无损锚点」双通道**；
4. **长度控制：300（软目标）+ 400（硬护栏）双层，不是一回事**：
   - SUMMARY_PROMPT 的 ≤300 字是**质量目标**——期望摘要紧凑，但指令没有强制力（三组 36 轮中 11 轮超限，实测分布 305~367 字）；
   - `hard_cap=400` 是**失控护栏**，不是达标线。为什么设 400 而不是 300：三组实测上界 367 字、超 300 是常态（36 轮 11 次），若硬顶设在 300，这些"略超目标"的正常波动全部变成截断——把"摘要略长"这个轻问题升级成"摘要尾部被切"的确定性损伤。400 位于实测分布上界之外，只在模型彻底无视指令时触发（本实验 36 轮 0 触发，B 组 max 347）；
   - **截断的风险是真实存在的，不回避**：若触发，截断点可能落在一句承诺或订单信息中间，造成新的损伤。当前的缓解与定位：硬截断保护的是**上下文预算的确定性上界**（防止异常超长摘要把下游窗口挤爆），且实体在压缩时已先行入锚、不受摘要截断影响；但被截掉的尾部语义承诺确实可能丢——这是已知未解问题，根治方向是结构化摘要（§7 遗留），截断只是让它从"不可控的超长"变成"有界的尾部截断"。

**设计取舍（追问高发区）**：为什么不用 LLM 抽实体？——抽取结果会进锚点段成为"事实源"，若抽取本身是 LLM 的，锚点的可靠性就退化为另一个概率问题；正则对结构化标识符是精确解。语义承诺（"15 天无理由"）表述多样、正则覆盖不了，**诚实地留给摘要通道，由分类别指标暴露它的保留率**。

## 6. A/B 对照结果与 metric 变化

三组同配置（t=10/k=3，各 12 次调用）：A1 首跑、A2 复测（估方差）、B 组（pin + hard_cap）：

| 指标 | A1 基线 | A2 复测 | B（pin+cap） | 变化解读 |
|---|---|---|---|---|
| final retention（macro） | 96.3% | 88.89% | 96.3% | B 与 A1 持平，但含金量不同（见解读②） |
| final retention（pooled） | 96.0%（24/25） | 88.0%（22/25） | 96.0%（24/25） | 两口径结论一致 |
| summary_reliant（macro）* | 95.83% | 87.5% | 95.83% | B−A2 差 8.3pt，为点估计（见 §6.2） |
| summary_reliant（pooled）* | 94.1%（16/17） | 82.4%（14/17） | 94.1%（16/17） | 分母仅 17 条，单条 = ±5.9pt |
| **promise 类（pooled，8 条）** | 87.5%（7/8，丢1） | **62.5%（5/8，丢3）** | **87.5%（7/8，丢1）** | 实验观察：与锚点机制无关（见解读③） |
| **非 promise 事实（pooled，17 条）** | 100% | 100% | 100% | 全程无丢失（与 reliant 分母 17 恰好同值，属巧合） |
| 锚点覆盖 | — | — | 8/8 实体入锚 | 订单号/序列号/税号全部命中本组正则 |
| 压缩比 | 2.64x | 2.98x | 2.36x | 锚点段成本，明算账 |
| 摘要超 300 字轮数 | 4/12（max 367） | 3/12（max 358） | 4/12（max 347） | 400 硬护栏三组均未触发 |

\* 口径：A1/A2 的 summary_reliant 是**纯摘要**找回率；B 组代码实现度量的是**锚点+摘要合并上下文**的 context_recoverability。用 B 组落盘的纯摘要文本重算纯摘要口径，结果与合并口径逐位相同（95.83%/94.1%）——意味着**本轮实验锚点增量为零**：摘要恰好自己保住了全部实体，没有任何一条事实是"仅靠锚点"挽回的（详见解读②）。

**怎么读这张表（关键叙事）**：

1. **A1 vs A2 是同配置复测组**：两次运行 macro 读数差 7.5pt、pooled 差 8pt，b2b 丢 1 条 vs 丢 3 条——说明在当前配置下单次运行不足以代表稳定表现，这就是对照实验保留复测组、且所有组间差值只当点估计的原因；
2. **机制结果与实验观察必须分开说（最重要的一条）**：
   - 机制结果：B 组 8 条实体全部入锚——在「已入锚、未被 FIFO 淘汰、格式匹配」前提下，实体有了**独立于摘要的恢复路径**，是否存活不再完全依赖 LLM 摘要；
   - 实验观察：用落盘的纯摘要重算，B 组纯摘要找回率与"锚点+摘要"合并口径**逐位相同**——本轮实验中摘要恰好自己保住了全部实体，**锚点增量为零**，B 组 95.83% 全部由摘要贡献；
   - 结论：锚点的价值主张是**结构保险**（防 A2 式重写中"摘要丢实体"的运行），不是本轮的实测增量——本实验 36 轮中没有出现"摘要丢实体"的运行，保险未被触发；
3. **promise 类的组间差异是运行间波动，不能归因于锚点**：锚点正则不覆盖语义承诺，B 组 promise 7/8 与 A1 持平、高于 A2 的 5/8，只是这一次运行的摘要质量回落到首跑水平——A1 vs A2 已经示范了同配置可差 2 条，这个量级的差异在波动范围内；
4. **压缩比代价透明**：主对照是 B 2.36x vs 基线 A1 2.64x（锚点成本约 +0.28x，锚点段每脚本约 150 字符计入分母）；B vs A2（2.98x → 2.36x）的更大差值主要因为 A2 那次运行的摘要本身更长，不全是锚点成本。

### 6.2 结论边界（这组实验能证明什么、不能证明什么）

实验规模：3 个脚本 × 4 轮压缩 × 25 条 gold 事实；单模型（deepseek-v4-flash）、单 temperature（0.3）、单语言（中文）、单组参数（t=10/k=3）。

**能支持的结论**：

- 机制可行性：正则抽取 + 锚点注入对本评测集的 8 条目标实体实现 8/8 覆盖，且未引入实体类丢失、无增量损伤；
- 方法论观察：在当前配置下，相同脚本的两次运行出现了明显的保留率差异（96.3% vs 88.89%）——说明单次运行不足以代表稳定表现，因此对照实验保留复测组，所有差值视为点估计而非稳定的性能承诺；
- 漂移机制的存在：事实级轨迹证实一次重写可抹掉此前多轮连续保留的信息（A2 round4 三条承诺同时消失）。

**不能支持的结论（主动交代）**：

- **效应量的精确估计**：所有差值都是无置信区间的点估计。reliant 分母仅 17 条（单条 = ±5.9pt）、promise 类仅 8 条（单条 = ±12.5pt）；
- **"pinned facts 改善了语义承诺保留率"**：锚点不覆盖 promise 类，B 组 7/8 vs A2 组 5/8 的差异在已观测的运行间波动范围内，无机制归因路径——现有实验不能证明这个命题；
- **"锚点产生了实测挽回"**：本轮实验锚点增量为零（纯摘要口径与合并口径逐位相同），锚点的实际挽回效果在本数据集上未被触发，只有机制层面的结构保证；
- **跨模型 / 跨参数泛化**：仅在 deepseek-v4-flash + t=10/k=3 + 中文脚本下成立；换模型（摘要风格不同）或加大窗口（reliant 分母会更小）需重测；
- **锚点正则的完备性**：8/8 是"评测集内目标实体"的覆盖结论，不等于正则对任意真实对话的实体召回率。

## 7. 诚实的 trade-off 与遗留

- **语义承诺类仍会丢**：`invoice_type` 这类无结构化特征的承诺不可正则锚定，目前靠摘要通道 + 分类指标暴露。下一步候选是**结构化摘要**（摘要输出字段化模板：订单/承诺/偏好分栏），让承诺也有槽位兜底；
- **硬截断三组均未触发**（max 347 < 400），它是保险而非收益来源——但发现②（36 轮 11 轮超 300 字）说明没有它就是在裸奔；
- **指标口径的代码化拆分待做**：当前 runner 的 `summary_reliant_retention` 属性在 pin 模式下实际度量 context_recoverability（锚点+摘要合并），本报告用落盘的纯摘要文本离线重算区分了两口径；正确做法是 runner 层拆成两个独立属性并分别落盘；
- **宏观 decay 曲线的伪影待修**：早期轮次未发生的事实拉低读数，若要真实的"逐轮退化曲线"，应对齐"事实首次出现后的轮次"计算；当前可靠工具是单条事实的逐轮轨迹；
- **实体误报可接受**：弱 token（如 wifi6password，仅 1 个数字）通过"字母数字各 ≥2"规则排除；紧凑日期会被钉住，属无害误报；
- **评测本身的天花板**：gold 是最小关键字符串匹配，"语义等价改写"（换个说法但意思对）会漏报为丢失——这是确定性断言换 LLM judge 的主动取舍：可复现、零成本、秒级，且对"实体是否原文在场"这个核心问题足够。

## 8. 面试追问 Q&A 备忘

- **锚点实际挽回了什么？** 诚实回答：本轮实验**零增量**——三组运行的摘要恰好都保住了全部实体，纯摘要口径与"锚点+摘要"口径逐位相同。锚点的价值是结构保险：它保证"摘要丢实体"这种运行（A2 式重写风险）发生时实体仍可从锚点恢复，而本实验没有出现这种运行，保险未被触发。用压缩比 0.28x 的成本买一个对高风险小概率事件的兜底，与买保险的逻辑一致；
- **B 组 promise 保留率比 A2 高，是锚点的功劳吗？** 不是。锚点正则不覆盖语义承诺，这个差异在已观测的运行间波动范围内（同配置两次运行差 2 条是已发生事实），现有实验不能证明锚点改善了承诺保留率；
- **decay 曲线是上升的，压缩不是越压越差吗？** 那是评测伪影：早期轮次大量事实还没在对话里发生，读数被拉低。可靠的分析工具是单条事实的逐轮轨迹（哪轮在、哪轮被抹），宏观曲线在本数据集上不可解读；
- **为什么硬护栏是 400 不是 300？** 300 是质量目标（prompt 层），400 是失控护栏（代码层）。三组实测上界 367、超 300 是常态（36 轮 11 次），硬顶设 300 会把这些正常超限变成确定性截断损伤；400 只在模型彻底无视指令时触发（本实验 0 触发）；
- **如果截断真的切在承诺句中间怎么办？** 承认这是真实风险：截断保护的是上下文预算上界，代价是尾部可能截断。缓解：实体在压缩时已先行入锚不受影响；触发本身是异常信号（应排查 prompt/模型行为），根治靠结构化摘要给承诺留槽位；
- **为什么压缩触发用消息条数不用 token？** 教学项目用条数近似阈值，token 计数是 obvious 升级项（tiktoken 一行），机制设计与触发条件解耦，不影响 harness 复用；
- **为什么保留窗口 k=3 而不是动态？** k 是 harness 的实验变量（CLI 可调），固定值保证 A/B 可比；
- **pinned 淘汰策略？** FIFO 上限 30：防膨胀优先，客服场景近期订单更常被追问，淘汰最旧符合业务直觉；
- **和 LangGraph checkpointer 的关系？** 正交：checkpointer 管跨进程状态恢复，压缩管单会话内上下文预算；
- **这个 harness 还能评什么？** 任何 `(old_messages, prev_summary) -> str` 的摘要器都能插进来对比（离线 truncate/extractive 基线已内置），后续 plan_execute 路径的 step_results 紧缩也计划复用同一套方法。
