# 追问三场景 · 手工验证用例

> 对应 docs/plan-execute-design.md §2 三张控制流图。
> 前置：`.env` 配 `PLAN_EXECUTE_ENABLED=true`，`python main.py` 启动后横幅显示「Plan-and-Execute 规划执行模式」。
> 离线对照：用例 L / J / K（`python -m unittest tests.test_plan_execute_graph`）。

## 场景 1：候选追问 → 恢复原计划

**验证路径**：executor `needs_clarify`（idx 不动）→ review → clarify → 回答入 messages → executor 重试**同一 step** → 成功后 idx+1 继续剩余步骤。

| 步 | 操作 | 预期观察 |
|----|------|---------|
| 1 | 输入 `我要退款` | `🧭 [planner v1]` 只出现一次；`🔧 list_user_orders` 执行一次 |
| 2 | 追问「为哪个订单」时输入 `1`（任选其一） | ❓ 渲染候选序号列表；回答后**不出现** `🧭 [planner v2]`（无重规划） |
| 3 | 追问「退款原因」时输入 `1` | `🔧 apply_refund` 被调用，args 中 order_id = 第 2 步所选订单 |

**通过标准**：
- `list_user_orders` 全程只执行一次（已完成的 step 不重跑）
- 追问后计划继续推进直至 generate，最终回复确认的订单 = 所选订单

## 场景 2：补充第二字段时第一字段不丢

**验证路径**：两轮 clarify 问答均 append 进 messages；executor 重试时上下文同时含两轮回答（原 bug：第二轮覆盖 `clarified_answer` 单槽位 → 重复追问订单）。

| 步 | 操作 | 预期观察 |
|----|------|---------|
| 1 | 输入 `我要退款` | 第一问：为哪个订单退款 |
| 2 | 输入 `1`（Nike 运动鞋） | 第二问：退款原因（问题中应回显已选订单，如「您要退款的是 Nike…」） |
| 3 | 输入 `1`（尺码不合适） | **不再第三次追问订单**；直接 `🔧 apply_refund` |

**通过标准**：
- 无重复追问（对照上方 2026-10-19 实录第 50 行的 bug 现象）
- `apply_refund` 的 args 同时含 order_id 和 reason 两个字段

## 场景 3：追问中改变目标 → 重新规划

**验证路径**：executor `needs_replan`（idx 不动）→ review 快路径确定性 replan（不调 LLM）→ planner v2 从 messages 读到新意图 → 计划整体替换 → 从头执行。

| 步 | 操作 | 预期观察 |
|----|------|---------|
| 1 | 输入 `我要退款` | `🧭 [planner v1]`；出现退款流程追问 |
| 2 | 追问订单时输入 `不退了，帮我查一下小米14 Ultra的物流` | 依次出现：`🔎 [executor] 目标已变 → 请求重规划` → `🔎 [review] 目标已变 → replan` → `🧭 [planner v2] 生成 N 个步骤（重规划）` |

**通过标准**：
- `🔧 query_logistics` 被调用；`apply_refund` **全程未被调用**
- 最终回复是物流信息而非退款结果
- 若继续闲聊「那还是算了吧」，agent 如实兜底而非强行执行旧计划

## 场景 4：闲聊短路（成本回归）

**验证路径**：planner 判无需计划 → 输出 `{"action": "direct_reply", ...}` → plan 为空 → 条件边直转 generate → generate 透传不调 LLM。
**修复背景**：旧契约把闲聊降级成"直接回复用户"步骤，白跑 executor + review（3 次 LLM）。

| 步 | 操作 | 预期观察 |
|----|------|---------|
| 1 | 输入 `你好` | 只有 `🧭 [planner v1] 无需规划 → 直接回复`；**不出现** `🔧 [执行]`、也不出现 review 的 `🔎` 行 |
| 2 | 输入 `你能做什么` | 同上；回复直接可读，不啰嗦 |

**通过标准**：
- 无任何工具调用、无 step 执行日志
- 观察到 generate 未产生额外 LLM 调用（全链仅 planner 1 次；若接了 LangSmith，trace 中该轮只有 planner + generate 两个节点、一次 LLM run）
- 对照：输入 `帮我查一下最近的订单` 仍应走完整链路（planner → executor → review → generate）
